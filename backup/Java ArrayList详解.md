### 一、 底层：Object[] 数组，默认容量 10

`ArrayList` 的本质是一个**动态数组**，其内部维护了一个 `Object[] elementData` 数组来存储元素。

#### 1. 默认容量的版本差异（重要考点）
* **JDK 1.7 及之前**：在调用无参构造函数 `new ArrayList()` 时，会**立即**创建一个长度为 10 的 `Object[]` 数组。
* **JDK 1.8 及之后（当前主流）**：采用了**懒加载（延迟初始化）** 优化。无参构造函数只会将 `elementData` 赋值为一个**空数组**（`DEFAULTCAPACITY_EMPTY_ELEMENTDATA`）。**只有在第一次调用 `add()` 方法时**，才会将其初始化为默认容量 **10**。
  * *优化目的*：避免创建大量 `ArrayList` 却未使用时造成的内存浪费。

#### 2. 内存特性
数组在 JVM 堆内存中是**连续分配**的，这是它后续所有性能特点（查询快、增删慢）的物理基础。

---

### 二、 扩容：1.5 倍（oldCapacity + (oldCapacity >> 1)）

当数组容量不足时，`ArrayList` 会自动扩容。

#### 1. 扩容计算公式
源码中的核心代码为：
```java
int oldCapacity = elementData.length;
int newCapacity = oldCapacity + (oldCapacity >> 1);
```
* `oldCapacity >> 1` 是位运算，相当于将旧容量**除以 2**（向下取整）。
* 因此，`新容量 = 旧容量 + 旧容量/2 = 旧容量的 1.5 倍`。
* *例如：容量 10 -> 扩容为 15 -> 22 -> 33 -> 49...*

#### 2. 为什么使用位运算 `>> 1`？
在计算机底层，**位移运算的执行效率远高于乘除法运算**。使用 `>> 1` 代替 `/ 2` 或 `* 1.5`，可以提升扩容计算时的微小性能。

#### 3. 为什么是 1.5 倍而不是 2 倍？
这是 `ArrayList` 设计中最精妙的地方之一，主要出于**内存复用**的考量：
* **如果是 2 倍扩容**（10 -> 20 -> 40 -> 80）：每次扩容释放的旧内存块（10, 20, 40），无论怎么拼接，都**永远无法**满足下一次扩容（80）的需求，容易造成内存碎片。
* **如果是 1.5 倍扩容**（10 -> 15 -> 22 -> 33 -> 49）：经过几次扩容后，之前释放的较小内存块在 GC（垃圾回收）整理后，**有机会拼凑出足够大的连续内存**来满足后续的扩容需求，从而提高了内存的利用率。

#### 4. 扩容的底层动作
扩容时，会调用 `Arrays.copyOf(elementData, newCapacity)`，其底层依赖 Native 方法 `System.arraycopy()`，将原数组的数据**整体拷贝**到一块全新的、更大的连续内存中。

---

### 三、 add 流程：检查容量 → 插入 → size++

`ArrayList` 的 `add` 方法分为**尾部添加**和**指定位置添加**，流程略有不同：

#### 1. 尾部添加：`add(E e)`
1. **检查容量 (`ensureCapacityInternal`)**：
   * 判断当前 `size + 1` 是否大于数组长度。
   * 如果是首次添加，取 `默认容量10` 和 `size+1` 的最大值。
   * 如果容量不足，触发上述的 **1.5倍扩容** 流程。
2. **插入元素**：将元素赋值给 `elementData[size]`。
3. **size++**：将 `size` 属性加 1，返回 `true`。

#### 2. 指定位置添加：`add(int index, E element)`
1. **边界检查**：检查 `index` 是否在 `0` 到 `size` 之间（注意：可以等于 `size`，相当于尾部添加）。
2. **检查容量**：同尾部添加，必要时扩容。
3. **移动元素（核心耗时点）**：
   * 计算需要移动的元素个数：`numMoved = size - index`。
   * 如果 `numMoved > 0`，调用 `System.arraycopy()` 将 `index` 及其后面的所有元素，**向后移动一位**。
4. **插入元素**：将新元素放入空出的 `elementData[index]`。
5. **size++**：`size` 加 1。

---

### 四、 为什么查询快、增删慢？

这是由数组的**物理内存结构**和**算法复杂度**共同决定的。

#### 1. 为什么查询快？（时间复杂度 $O(1)$）
* **内存连续性**：数组在内存中是连续分配的，且每个元素占用的内存大小相同。
* **寻址公式**：CPU 只需要知道数组的**首地址**和**每个元素的字节大小**，就可以通过数学公式直接计算出任意索引元素的物理内存地址：
  `目标地址 = 首地址 + (index × 元素大小)`
* **无需遍历**：因为可以直接计算出地址，所以无论查询第一个还是第一万个元素，都只需要一次计算，时间复杂度为 $O(1)$。
* **CPU 缓存友好**：连续的内存布局非常契合 CPU 的 **Cache Line（缓存行）** 预取机制（空间局部性原理），能极大减少 CPU 访问主存的次数，进一步提升查询速度。

#### 2. 为什么增删慢？（时间复杂度 $O(n)$）
* **插入慢（指定位置）**：在中间插入元素时，为了保持数组的连续性，必须将插入位置后的所有元素**向后挪动一位**。如果数组有 10000 个元素，在索引 0 处插入，就需要移动 10000 个元素。
* **删除慢**：同理，删除中间元素后，必须将后面的所有元素**向前挪动一位**以填补空缺。
* **底层拷贝开销**：虽然 `System.arraycopy()` 是底层 C/C++ 实现的 Native 方法，比 Java 层的 `for` 循环快得多，但当数据量庞大时，**大量的内存数据搬运**依然会消耗可观的 CPU 时间和内存带宽。
* *(注：如果是纯粹的**尾部添加/删除**，且**不触发扩容**，时间复杂度是 $O(1)$，是非常快的。)*

---

### 💡 总结与最佳实践

基于以上原理，在实际开发中使用 `ArrayList` 时应遵循以下最佳实践：

1. **预估容量，避免扩容**：如果能提前知道集合的大小，请在构造时指定初始容量 `new ArrayList<>(expectedSize)`，避免底层频繁触发 1.5 倍扩容和数组拷贝。
2. **尽量尾部操作**：在业务允许的情况下，尽量使用 `add(E e)` 进行尾部添加，避免使用 `add(int index, E e)` 在中间插入。
3. **批量删除用倒序或迭代器**：如果需要删除多个元素，不要使用 `for` 正序循环调用 `remove(index)`（会导致严重的元素移动和索引错位），应使用 `Iterator` 的 `remove()` 方法，或倒序遍历删除。
4. **频繁增删考虑 LinkedList**：如果业务场景是**极高频的中间位置增删**，且**极少随机查询**，应考虑使用 `LinkedList`（但需注意 `LinkedList` 节点内存开销大且对 CPU 缓存不友好，现代开发中通常更推荐直接用 `ArrayList` 配合算法优化，或评估是否真的需要链表）。
