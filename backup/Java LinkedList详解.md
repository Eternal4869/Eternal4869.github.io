与 `ArrayList` 的连续内存不同，`LinkedList` 的设计哲学完全建立在**离散内存**之上。

---

### 一、 底层：双向链表 Node(prev, item, next)

`LinkedList` 的本质是一个**双向链表**，它不要求内存连续，而是通过“指针”将分散在堆内存中的节点串联起来。

#### 1. 节点结构 (Node)
在 `LinkedList` 内部，定义了一个静态内部类 `Node` 来存储数据和指针：
```java
private static class Node<E> {
    E item;           // 存储的实际数据
    Node<E> next;     // 指向后继节点的指针
    Node<E> prev;     // 指向前驱节点的指针

    Node(Node<E> prev, E element, Node<E> next) {
        this.item = element;
        this.next = next;
        this.prev = prev;
    }
}
```

#### 2. 链表的整体结构（版本差异考点）
* **JDK 1.6 及以前**：采用的是**循环双向链表**。内部有一个特殊的 `header` 节点，它的 `prev` 指向尾节点，`next` 指向头节点，尾节点的 `next` 和头节点的 `prev` 都指向 `header`。
* **JDK 1.7 及之后（当前主流）**：为了节省内存，**去掉了 `header` 节点**，改为了**普通的双向链表**。
  * 维护了两个核心属性：`transient Node<E> first;`（头节点）和 `transient Node<E> last;`（尾节点）。
  * 头节点的 `prev = null`，尾节点的 `next = null`。

#### 3. 内存特性
与数组不同，`LinkedList` 的节点在 JVM 堆内存中是**分散分配**的。每次 `new Node()` 时，JVM 会在堆中寻找一块足够放下该节点的内存，这些内存块在物理地址上**通常是不连续的**。

---

### 二、 核心操作中的“折半优化”

在理解快慢之前，必须知道 `LinkedList` 在源码层面做了一个非常聪明的优化：**双向遍历（折半查找）**。

无论是查询、插入还是删除，只要涉及到根据索引 `index` 找节点，源码都会先判断 `index` 离头近还是离尾近：
```java
Node<E> node(int index) {
    // 核心优化：如果 index 小于 size 的一半，从头往后找；否则从尾往前找。
    if (index < (size >> 1)) { 
        Node<E> x = first;
        for (int i = 0; i < index; i++) x = x.next;
        return x;
    } else {
        Node<E> x = last;
        for (int i = size - 1; i > index; i--) x = x.prev;
        return x;
    }
}
```
*这个优化让链表在中间位置操作时的遍历次数减少了一半，但并没有改变其 $O(n)$ 的本质。*

### 三、 为什么查询慢、增删快？（深度剖析与误区排雷）

这是面试中最常问的问题，但**90% 的回答都是不准确的**。我们必须打破“LinkedList 增删一定比 ArrayList 快”的刻板印象，分场景来剖析。

#### 1. 为什么查询慢？（时间复杂度 $O(n)$）
* **无法随机访问**：因为内存不连续，无法像数组那样通过 `首地址 + 偏移量` 直接计算出目标地址。必须从 `first` 或 `last` 开始，顺着 `next` 或 `prev` 指针**一步步遍历**。
* **CPU 缓存极不友好（致命伤）**：现代 CPU 读取内存时，会将连续的一块数据加载到 Cache（缓存行）中。`ArrayList` 的连续内存完美契合这一点；而 `LinkedList` 的节点分散在内存各处，访问下一个节点时，极大概率会触发 **Cache Miss（缓存未命中）**，导致 CPU 必须去慢速的主存中重新读取数据。**这种底层的硬件级延迟，是链表查询极慢的核心原因。**

#### 2. 为什么增删“快”？（严格界定条件）
说它增删快，**必须加上严格的前提条件**：

* **真正的快（$O(1)$）：头部/尾部增删**
  * 如果只是在链表的最前面或最后面添加/删除元素，不需要遍历，直接修改 `first` 或 `last` 指针即可。此时时间复杂度是严格的 $O(1)$，确实比 `ArrayList` 快（`ArrayList` 头部插入需要移动所有元素）。

* **理论上的快（$O(1)$）：已知节点引用的中间增删**
  * 如果你**已经拿到了**要删除/插入位置的 `Node` 对象引用，只需要修改前后节点的指针（例如 `p.prev.next = p.next`），不需要移动任何其他元素。这个“修改指针”的动作是 $O(1)$ 的。

* **伪快（实际很慢）：根据索引在中间增删**
  * 如果你只知道 `index`（比如 `list.remove(5000)`），`LinkedList` 必须先**遍历**找到第 5000 个节点（耗时 $O(n)$，且因为 CPU 缓存不友好，遍历极慢），然后再修改指针（$O(1)$）。
  * **总耗时 = 慢速遍历 + 修改指针**。在这种情况下，`LinkedList` 的增删**远远慢于** `ArrayList`（`ArrayList` 虽然需要 `System.arraycopy` 移动元素，但它是底层 C++ 实现的连续内存块拷贝，速度极快，且对 CPU 缓存友好）。

---

### 四、 内存开销对比（隐藏的成本）

除了性能，`LinkedList` 的内存占用也远大于 `ArrayList`：
* **ArrayList**：只存储元素的引用（64位系统开启指针压缩后为 4 字节/个）。
* **LinkedList**：每个节点除了存储元素引用（4字节），还要存储 `prev` 和 `next` 两个指针（各 4 字节），再加上 Java 对象头（12或16字节），**一个节点的实际内存开销至少是数据本身的 3 到 4 倍**。

### 💡 总结与实战最佳实践

基于以上底层原理，在实际开发中请遵循以下原则：

1. **无脑首选 ArrayList**：在 99% 的业务场景中，`ArrayList` 的综合性能（查询、CPU缓存命中率、内存占用）都完胜 `LinkedList`。
2. **打破迷信**：**绝对不要**因为“中间增删多”就使用 `LinkedList`。在中间频繁增删时，`ArrayList` 的底层数组拷贝通常比 `LinkedList` 的链表遍历更快。
3. **何时使用 LinkedList**：
   * 只有当你明确需要**在头部和尾部进行极高频的增删**（例如实现消息队列、双端队列），且**几乎不需要通过索引查询**时，才考虑使用它。
   * *(注：即使在这种场景下，现代 Java 开发也更推荐使用 **`ArrayDeque`**，它基于循环数组实现，既具备头尾 $O(1)$ 增删的能力，又拥有数组对 CPU 缓存友好的优势，性能比 `LinkedList` 更好。)*
4. **迭代器删除**：如果非要遍历 `LinkedList` 并删除元素，务必使用 `Iterator.remove()`，它内部维护了当前节点的引用，删除时只需 $O(1)$ 修改指针，避免了重复遍历。
