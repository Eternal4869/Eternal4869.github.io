Redis 在内存使用达到 `maxmemory` 上限时，会通过 **`maxmemory-policy`** 配置项执行数据淘汰。官方共提供 **8 种淘汰策略**，按作用范围（`allkeys` / `volatile`）和算法可分为以下类别：

### 🔹 1. `noeviction`（默认策略）
- **行为**：不淘汰任何数据。内存满时，执行写命令直接返回 `OOM` 错误，读命令正常。
- **适用场景**：对数据完整性要求极高、不允许缓存丢失的场景（如配合外部持久化或业务层强管控）。

### 🔹 2. 基于 LRU（最近最少使用）
- `allkeys-lru`：从 **所有 key** 中淘汰最近最少访问的 key。
- `volatile-lru`：仅从 **设置了过期时间（TTL）的 key** 中淘汰最近最少访问的 key。
- **适用场景**：经典缓存场景，优先保留近期活跃的热点数据。

### 🔹 3. 基于 LFU（最不经常使用）*（Redis 4.0+）*
- `allkeys-lfu`：从 **所有 key** 中淘汰历史访问频率最低的 key。
- `volatile-lfu`：仅从 **设置了过期时间的 key** 中淘汰访问频率最低的 key。
- **适用场景**：数据热度相对稳定，希望抵抗“偶然突发访问”对缓存的干扰，比 LRU 更适合长期热点保护。

### 🔹 4. 基于 Random（随机）
- `allkeys-random`：从 **所有 key** 中随机淘汰。
- `volatile-random`：仅从 **设置了过期时间的 key** 中随机淘汰。
- **适用场景**：对缓存命中率要求不高，追求极低 CPU 开销的简单场景。

### 🔹 5. 基于 TTL（剩余存活时间）
- `volatile-ttl`：仅从 **设置了过期时间的 key** 中，淘汰 TTL 剩余时间最短的 key。
- **适用场景**：希望优先清理即将自然过期的数据，降低主动过期检查的额外开销。

---

### ⚙️ 配置方式
```conf
# redis.conf
maxmemory 2gb
maxmemory-policy allkeys-lru
```
运行时动态修改：
```bash
CONFIG SET maxmemory-policy allkeys-lfu
```

---

### 💡 选型建议
| 场景 | 推荐策略 |
|------|----------|
| 通用缓存（大多数业务） | `allkeys-lru` 或 `allkeys-lfu` |
| 强依赖过期机制，且不想误删未设 TTL 的业务数据 | `volatile-lru` / `volatile-lfu` |
| 缓存数据价值均等，追求极简实现 | `allkeys-random` |
| 希望优先清理快过期的数据 | `volatile-ttl` |
| 绝对不允许丢数据（如配合强一致性架构） | `noeviction` |

### ⚠️ 注意事项
1. **LRU/LFU 均为近似算法**：Redis 为兼顾性能，采用**采样淘汰**（默认采样 5 个 key，可通过 `maxmemory-samples` 调高至 10）。精度略低于理论值，但生产环境命中率通常已足够。
2. **`volatile-*` 策略不淘汰无 TTL 的 key**：若业务大量写入未设置过期时间的 key，可能导致内存满却无法淘汰，最终触发 `OOM`。
3. **生产环境慎用 `noeviction` 作缓存策略**：极易因突发写入导致服务雪崩，建议至少配置 `allkeys-lru` 并在应用层做好降级/限流。

---

LRU和LFU的区别

LRU（Least Recently Used）和 LFU（Least Frequently Used）是缓存淘汰的两种核心算法，**本质区别在于“淘汰依据不同”**：LRU 看**最近一次访问时间**，LFU 看**历史访问总频率**。

下面从原理、优缺点、Redis 实现细节和适用场景四个维度对比：

### 📊 核心对比一览
| 维度 | LRU（最近最少使用） | LFU（最不经常使用） |
|:---|:---|:---|
| **淘汰依据** | 距现在最久没被访问的 key | 历史访问次数最少的 key |
| **关注点** | 时间局部性（Recency） | 频率局部性（Frequency） |
| **对抗缓存污染** | ❌ 弱（批量扫描会瞬间踢出热点） | ✅ 强（高频 key 仍保留） |
| **新数据存活率** | ✅ 高（新访问即变“最近”） | ❌ 低（新 key 频率低易被误杀） |
| **内存/CPU 开销** | 较低（维护访问顺序） | 较高（维护计数器+衰减逻辑） |
| **典型适用场景** | 热点随时间快速变化、突发流量多 | 长期热点稳定、访问分布极度不均 |

---

### 🔍 深入解析

#### 1. LRU 的行为特征
- **机制**：每次访问 key 时，将其移到“最近访问”位置；内存满时淘汰“最久未动”的 key。
- **致命缺陷**：**缓存污染（Cache Pollution）**。例如定时任务扫描 10 万条冷数据，这些冷数据会瞬间变成“最近访问”，把真正的热门商品/配置挤出缓存，导致命中率骤降。
- **优势**：对新数据极其友好，适合热点快速轮转的场景（如新闻流、实时排行榜）。

#### 2. LFU 的行为特征
- **机制**：记录每个 key 被访问的次数，淘汰次数最少的。
- **致命缺陷**：**新数据冷启动问题**。刚写入的 key 计数为 0 或 1，极易被当成“冷数据”淘汰。
- **Redis 的解法**：引入 **访问频率衰减（Aging）**。定期将所有 key 的计数器按比例下降，让新数据有机会“涨分”，老数据热度自然衰减。配合对数计数器，兼顾精度与内存。

---

### ⚙️ Redis 实现细节（非严格算法，均为近似）
| 策略 | Redis 实现方式 | 关键配置参数 |
|:---|:---|:---|
| **LRU** | 随机采样 `maxmemory-samples` 个 key（默认 5），从中淘汰最久未访问的。不维护全局链表，省内存。 | `maxmemory-samples`（调至 10 可提升精度，但增加 CPU） |
| **LFU** | 24-bit 计数器：高 16 位存最后访问时间（分钟），低 8 位存对数访问计数（0~255）。定期按 `lfu-decay-time` 衰减。 | `lfu-decay-time`（衰减周期，默认 1 分钟）<br>`lfu-log-factor`（计数增长曲线，默认 10） |

> 💡 **为什么不用严格 LRU/LFU？**  
> 严格实现需维护双向链表/精确计数器，内存和 CPU 开销随 key 数量线性增长。Redis 采用**采样+近似计数**，在 95%+ 命中率与极低开销之间取得平衡。

---

### 🎯 选型建议
| 业务特征 | 推荐策略 | 原因 |
|:---|:---|:---|
| 热点变化快、常有突发访问/定时任务扫描 | `allkeys-lru` | 新数据快速上位，抗突发能力强 |
| 长期热点稳定（如热门商品、字典配置） | `allkeys-lfu` | 保护高频 key，抗缓存污染 |
| 混合场景且无法预知访问模式 | `allkeys-lfu`（调低 `lfu-log-factor` 至 5~8） | 让新 key 计数涨更快，平衡新旧数据 |
| 必须保留未设 TTL 的业务数据 | `volatile-lru` / `volatile-lfu` | 仅淘汰带过期时间的 key |

---

### 📌 实战调优提示
1. **LRU 命中率低**：先尝试调大 `maxmemory-samples 10`，观察 CPU 是否可接受。
2. **LFU 新数据频繁丢失**：调小 `lfu-log-factor`（如改为 `5`），让计数增长更敏感；或调大 `lfu-decay-time` 减缓衰减。
3. **监控验证**：通过 `INFO memory` 的 `evicted_keys` 和 `keyspace_hits`/`keyspace_misses` 评估实际命中率，不要仅凭理论选型。
